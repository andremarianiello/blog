Parsing JSON Data with Missing List Fields

Posted on January 4, 2025

The Problem of the Missing JSON Fields

I was recently working on a project that involved parsing JSON data generated from another system. Let’s say it looked something like this:

Literate Haskell Preamble 
{-# LANGUAGE OverloadedStrings #-}
{-# LANGUAGE DeriveAnyClass #-}
{-# LANGUAGE DerivingVia #-}
{-# LANGUAGE DuplicateRecordFields #-}
{-# LANGUAGE TypeFamilies #-}
{-# LANGUAGE UndecidableInstances #-}

import Data.Aeson
import Data.ByteString.Lazy
import Data.Coerce (coerce)
import Data.Maybe (fromMaybe)
import Data.Kind
import GHC.Generics
rawData :: ByteString
rawData = "{\"name\": \"Frank\", \"favoriteNumbers\": [1, 2, 3]}"

The data followed a preexisting schema, and I wanted to write data types with derived FromJSON instances to parse the data into.

data MyData = MyData
  { name :: String
  , favoriteNumbers :: [Int]
  }
  deriving (Show, Generic)
>>> deriving instance FromJSON MyData
>>> eitherDecode rawData :: Either String MyData
Right (MyData {name = "Frank", favoriteNumbers = [1,2,3]})

This is pretty standard stuff so far. The issue I ran into was that some of the fields in objects in this data set were optional arrays of values. This meant I needed to parse data that could look like this:

rawDataWithoutField :: ByteString
rawDataWithoutField = "{\"name\": \"Sandra\"}"

But the standard FromJSON instance doesn’t know how to handle this!

>>> deriving instance FromJSON MyData
>>> eitherDecode rawDataWithoutField :: Either String MyData
Left "Error in $: parsing Main.MyData(MyData) failed, key \"favoriteNumbers\" not found"

This problem is definitely solvable, but what is the best way to solve it?

A Few Solutions That I Didn’t Choose (and Why!)

The most interesting problems don’t only have one best solution: usually there are multiple solutions with different pros and cons. These are the solutions I decided against using. You can skip this section if you want to get right to the solution I went with.

Wrap the Field in a Maybe

Now, Aeson provides a standard way of handling omitted fields: wrap it in a Maybe!

data MyMaybeData = MyMaybeData
  { name :: String
  , favoriteNumbers :: Maybe [Int]
  }
  deriving (Show, Generic, FromJSON)
>>> eitherDecode rawData :: Either String MyMaybeData
Right (MyMaybeData {name = "Frank", favoriteNumbers = Just [1,2,3]})
>>> eitherDecode rawDataWithoutField :: Either String MyMaybeData
Right (MyMaybeData {name = "Sandra", favoriteNumbers = Nothing})

Most of the time this solution is great, but I don’t love it in this case. The reason is that I wanted to treat the absence of the favoriteNumbers field as an empty list, but this technique would give me a Nothing value instead. [Int] already captures exactly the information that I want to store in my data type, so by introducing a possible Nothing value we introduce distinction between two cases that I don’t want people using my type to have to think about. For them, Nothing and Just [] should be equivalent.

Hand-Written FromJSON Instance

There is nothing stopping us from throwing out the derived FromJSON instance and hand-writing an instance that includes the Maybe [Int] -> [Int] logic that we want.

>>> instance FromJSON MyData where parseJSON = withObject "MyData" $ \v -> MyData <$> v .: "name" <*> v .:? "favoriteNumbers" .!= []
>>> eitherDecode rawDataWithoutField :: Either String MyData
Right (MyData {name = "Sandra", favoriteNumbers = []})

The problem I had with this approach was that I actually have dozens of custom data types to handle, meaning that I would have to write dozens of custom instances by hand. If they all had their own unique logic that could definitely be the right approach, but I just needed this same exact logic for all of my instances. Ultimately I didn’t like this solution because of the amount of boilerplate required to define these instances, not to mention the amount of effort required to keep those instances up-to-date with future changes to the data types.

Create a Type Specifically for Parsing JSON (aka a DTO)

One alternative approach would be to provide a special data type for parsing the JSON, and then manually converting to the real domain datatype.

data MyDataDTO = MyDataDTO
  { name :: String
  , favoriteNumbers :: Maybe [Int]
  }
  deriving (Show, Generic, FromJSON)

dtoToDomain :: MyDataDTO -> MyData
dtoToDomain MyDataDTO{name, favoriteNumbers} =
  MyData{name = name, favoriteNumbers = fromMaybe [] favoriteNumbers}
>>> instance FromJSON MyData where parseJSON json = dtoToDomain <$> parseJSON json
>>> eitherDecode rawDataWithoutField :: Either String MyData
Right (MyData {name = "Sandra", favoriteNumbers = []})

This approach is like the hand-written instances approach, except the instance logic is replaced with extra data types and conversion functions. I didn’t choose this approach because it’s similarities to the hand-written instance solution bring the same downsides.

Use a Higher-Kinded Type Parameter

Yet another approach I considered was similar to the DTO approach, but to use a parameterized data type to represent both the DTO and domain type.

data MyHKData f = MyHKData
  { name :: String
  , favoriteNumbers :: f [Int]
  }
  deriving (Generic)
deriving instance FromJSON (f [Int]) => FromJSON (MyHKData f)

This approach has the upside of eliminating the DTO data type, but it has the downside of being highly invasive of our domain datatype. It introduces a parameter that we only need when parsing JSON, but we have to keep it and be aware of it everywhere we use our domain data type. I really just want to use the data type that I wrote!

Use a Custom OmittableList

The final approach that I ended up not using was to define a special newtype

newtype OmittableList a = OmittableList [a] deriving Show

With a FromJSON instance that supports being omitted

instance FromJSON a => FromJSON (OmittableList a) where
  parseJSON = fmap OmittableList . parseJSON
  omittedField = Just (OmittableList [])

And then to use that newtype instead of a normal list in my type

data MyDataOL = MyDataOL
  { name :: String
  , favoriteNumbers :: OmittableList Int
  }
  deriving (Show, Generic, FromJSON)

-- >>> eitherDecode rawDataWithoutField :: Either String MyDataOL
-- Right (MyDataOL {name = "Sandra", favoriteNumbers = OmittableList []})

Of the solutions I have shown so far I like this one the most, but it is still more invasive than I like because it couples the type definition together with the JSON representation of our type.

So…What Solution is Good Enough??

So I rejected the above solutions because they didn’t satisfy one or both of the following criteria:

  • Let me use my original data type, unchanged
  • Don’t require too much boilerplate

Eventually I settled on a solution based on GHC’s DerivingVia extension, which meets both my criteria. The main reason that this wasn’t the immediate first choice is because it requires working with Generic representations, which is a bit more complicated than the other approaches discussed above. However, I think it is worth it. Let’s walk through how this approach works step by step.

Creating a Newtype Wrapper

First, let’s derive our instance

deriving via MyDataWithOmittableLists
  instance FromJSON MyData

Note: This is the syntax for using DerivingVia with StandaloneDeriving, but StandaloneDeriving is not required! This approach works with a standard DerivingVia clause.

This is saying that GHC should use the FromJSON instance from MyDataWithOmmittableLists to deriving a FromJSON instance for MyData. Because GHC implements this derived instance using coerce from Data.Coerce, this will only work if MyDataWithOmmittableLists is representationally equal to MyData.

So now we need to define MyDataWithOmittableLists

type MyDataWithOmittableLists = WithOmittableLists MyData

…but what is WithOmittableLists? We ultimately need our solution to scale up to dozens of types, so we can’t just define a single concrete type for MyData.

newtype WithOmittableLists a = WithOmittableLists
  { unWithOmittableLists :: a }
  deriving Show

Instead we will use a parameterized newtype wrapper. It is a newtype so that we get the representational equality we need, and we use the parameter to let us reuse this type to derive instances for all our types.

Creating Our Generic Instance

Now we need a FromJSON instance for our wrapper. We want this instance to behave just like the deriving instance for the inner type, except it should behave as if the list fields of our inner type were wrapped in Maybe. This would let us omit them.

Ideally, we could write this instance using gFromJSON from Data.Aeson.Types.FromJSON, but that module is not exposed to us. Our next best option is to include these extra Maybe wrappers in the Generic representation of WithOmittableLists, and then derive the FromJSON instance from the Generic instance.

Let’s write the Generic instance first

instance (Generic a, GOmittableLists (Rep a))
    => Generic (WithOmittableLists a) where
  type Rep (WithOmittableLists a) = MaybeListsRep (Rep a)
  from = withOmittableLists . from @a . coerce
  to = coerce . to @a . withoutOmittableLists

type family MaybeListsRep (rep :: Type -> Type) where
  MaybeListsRep (Rec0 String) = Rec0 String
  -- here is the type-level business logic
  MaybeListsRep (Rec0 [a]) = Rec0 (Maybe [a])
  MaybeListsRep (M1 t m f) = M1 t m (MaybeListsRep f)
  MaybeListsRep (l :*: r) = MaybeListsRep l :*: MaybeListsRep r
  MaybeListsRep (l :+: r) = MaybeListsRep l :+: MaybeListsRep r
  MaybeListsRep rep = rep

class GOmittableLists rep where
  withOmittableLists :: rep x -> MaybeListsRep rep x
  withoutOmittableLists :: MaybeListsRep rep x -> rep x

So now we have a Generic instance that is built using a new class, GOmittableLists, and a closed type family, MaybeListsRep. MaybeListsRep maps a Generic representation to a similar representation where list fields are wrapped with Maybe. The GOmittableLists class provides the withOomittableLists and withOmittableLists methods, which map values between those two representation types.

Creating Our GOmittableLists Instances

Now that we have a typeclass for Maybe-fying list fields of Generic representations, we need instances. Let’s get the uninteresting instances out of the way first.

instance (GOmittableLists f) => GOmittableLists (M1 t m f) where
  withOmittableLists (M1 a) = M1 (withOmittableLists a)
  withoutOmittableLists (M1 a) = M1 (withoutOmittableLists a)

instance (GOmittableLists l, GOmittableLists r)
    => GOmittableLists (l :*: r) where
  withOmittableLists (l :*: r) =
    withOmittableLists l :*: withOmittableLists r
  withoutOmittableLists (l :*: r) =
    withoutOmittableLists l :*: withoutOmittableLists r

instance (GOmittableLists l, GOmittableLists r)
    => GOmittableLists (l :+: r) where
  withOmittableLists (L1 a) = L1 (withOmittableLists a)
  withOmittableLists (R1 a) = R1 (withOmittableLists a)
  withoutOmittableLists (L1 a) = L1 (withoutOmittableLists a)
  withoutOmittableLists (R1 a) = R1 (withoutOmittableLists a)

These are uninteresting because they simply delegate the Maybe wrapping logic to other instances by following the Generic representation structure.

Let’s look at the actual Maybe-wrapping logic now

instance {-# OVERLAPPABLE #-} (MaybeListsRep (Rec0 a) ~ Rec0 a)
    => GOmittableLists (Rec0 a) where
  withOmittableLists (K1 a) = K1 a
  withoutOmittableLists (K1 a) = K1 a

instance {-# OVERLAPPABLE #-} (MaybeListsRep (Rec0 [a]) ~ Rec0 (Maybe [a]))
    => GOmittableLists (Rec0 [a]) where
  withOmittableLists (K1 a) = K1 (Just a)
  withoutOmittableLists (K1 a) = K1 (fromMaybe [] a)

instance {-# OVERLAPPING #-} (MaybeListsRep (Rec0 String) ~ Rec0 String)
    => GOmittableLists (Rec0 String) where
  withOmittableLists (K1 a) = K1 a
  withoutOmittableLists (K1 a) = K1 a

With these three instances we can handle the actual fields, Rec0, of the representation type. The Rec0 a instance is used when mapping non-list fields, so it doesn’t do any maybe wrapping. The Rec0 [a] instance is used when mapping list fields, so we wrap and unwrap the value. This is the instance with the actual logic happening. The final Rec0 String instance is provided so that we treat String fields like non-list fields because we do not want String fields to be omittable, just list fields of other types. After all, the name field is required!

Now we can finally test our Generic instance! Let’s look at the Generic representation of MyData first

>>> :kind! Rep MyData
Rep MyData :: * -> *
= M1
    D
    ('MetaData
       "MyData"
       "Main"
       "posts-0.1.0.0-inplace-aeson-omittable-fields"
       'False)
    (M1
       C
       ('MetaCons "MyData" 'PrefixI 'True)
       (M1
          S
          ('MetaSel
             ('Just "name")
             'NoSourceUnpackedness
             'NoSourceStrictness
             'DecidedLazy)
          (K1 R [Char])
        :*: M1
              S
              ('MetaSel
                 ('Just "favoriteNumbers")
                 'NoSourceUnpackedness
                 'NoSourceStrictness
                 'DecidedLazy)
              (K1 R [Int])))

And we can compare that to the Generic representation for MyDataWithOmittableLists

>>> :kind! Rep MyDataWithOmittableLists
Rep MyDataWithOmittableLists :: * -> *
= M1
    D
    ('MetaData
       "MyData"
       "Main"
       "posts-0.1.0.0-inplace-aeson-omittable-fields"
       'False)
    (M1
       C
       ('MetaCons "MyData" 'PrefixI 'True)
       (M1
          S
          ('MetaSel
             ('Just "name")
             'NoSourceUnpackedness
             'NoSourceStrictness
             'DecidedLazy)
          (K1 R [Char])
        :*: M1
              S
              ('MetaSel
                 ('Just "favoriteNumbers")
                 'NoSourceUnpackedness
                 'NoSourceStrictness
                 'DecidedLazy)
              (K1 R (Maybe [Int]))))

Focus on the last line of each representation and notice that K1 R [Int] in the first has been replaced by K1 R (Maybe [Int])) in the second. This is the exact change we wanted to make to the representation! The hardest part is now complete and we are almost done!

Creating Our FromJSON Instance

We now have a wrapper type with a custom Generic instance. We wrapped the list fields of its representation with Maybe so that parsing would still succeed even if those fields were not present. All the remains is to derive our FromJSON instance using the underlying Generic instance.

deriving anyclass instance
  ( Generic (WithOmittableLists MyData)
  , GFromJSON Zero (Rep (WithOmittableLists MyData))
  ) => FromJSON (WithOmittableLists MyData)

The default implementations of the members of FromJSON are written using the type’s Generic instance, meaning we can derive the FromJSON instance we want using the anyclass deriving strategy. The newtype deriving strategy is also available, but trying to use such an instance would fail to terminate as the FromJSON (WithOmittableLists a) instance and the FromJSON MyData instance call each other infinitely.

Let’s try out our shiny new instance!

>>> eitherDecode rawDataWithoutField :: Either String (WithOmittableLists MyData)
Right (WithOmittableLists {unWithOmittableLists = MyData {name = "Sandra", favoriteNumbers = []}})

Perfect! And thanks to the fact that we derived FromJSON MyData via this instance earlier, we can parse directly in MyData

>>> eitherDecode rawDataWithoutField :: Either String MyData
Right (MyData {name = "Sandra", favoriteNumbers = []})

Success!

So Are We Done?

We have achieved everything we wanted to achieve at the beginning; we can parse JSON data with missing list fields into our own data type, using a derived instance, without have to do any manually conversions between wrapper types. We also learned a technique for manipulating Generic instances in order to derive FromJSON instances with special behavior.

But is that good enough? What if I have a type with some omittable list fields, and some required list fields? What if I have a type with omittable fields of other types? The good news is that this technique can be extended to handle those cases as well. The bad news is that this post is already incredibly long, so I will have to save those for another post. Goodbye!
